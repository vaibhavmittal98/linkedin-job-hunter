# LinkedIn Job Hunter — Project Overview

## Stack
- **Backend:** Python 3.12, FastAPI, SQLAlchemy, SQLite
- **Frontend:** React 18, TypeScript, Vite
- **LLM:** OpenRouter (deepseek-v4-flash) via httpx
- **Scraping:** Apify actor `cheap_scraper~linkedin-job-scraper` or Bright Data (switchable via `SCRAPER_PROVIDER`)
- **Scheduling:** APScheduler (BackgroundScheduler)
- **Auth:** JWT (python-jose) + bcrypt
- **PDF:** fpdf2

## Key Patterns

### Auth
- JWT stored in localStorage, sent as `Authorization: Bearer <token>`
- `get_current_user` dependency on protected endpoints
- Token expires in 24h → frontend auto-redirects to /login on 401

### Jobs are user-specific
- `Job.user_id` links to `UserProfile.id`
- All queries filter by `user_id`
- Deduplication: `linkedin_id` per user (not globally unique)

### Scraping flow
1. Frontend sends keywords + locations to `/api/scrape`
2. Router starts `_run_scrape` as BackgroundTask
3. `_run_scrape` calls `scrape_linkedin_jobs`, which dispatches to the backend selected by `SCRAPER_PROVIDER` (Apify or Bright Data); both trigger → poll → fetch
4. Each job is deduped, optionally scored, stored with `user_id`
5. Run logged in `scrape_runs` table

> Switching backends is env-only (`SCRAPER_PROVIDER=apify|brightdata`) + restart.
> Both return the same dict shape, so `_run_scrape` and the DB are unchanged.
> Bright Data can't be reached from local WSL (Cloudflare Gateway TLS); use EC2.

### Scoring
- Multi-criteria: skills_match, experience_level, tech_stack, domain_relevance, disqualifiers (each 0-10)
- Weighted average → 0-100 score
- Disqualifiers <= 2 (hard blocker) cap total at 15; 3-4 (soft) halves total
- Uses user's `cv_text` from DB
- Extended thinking via `LLM_REASONING_EFFORT` env var (opt-in, scoring only)

### Ask-about-job chat
- Stateless Q&A about a job + CV. Nothing persisted (like ad-hoc cover letters).
- `POST /api/jobs/{id}/chat` (job context from DB) and `POST /api/chat` (CV + optional pasted description).
- Frontend: shared `ChatBox` on JobDetail and CoverLetter pages.

### Cover Letters
- Generated by LLM with strict style rules (no buzzwords, no CV regurgitation)
- Refinement via chat (iterative rewrites)
- PDF export with name/contact extracted from CV

### Deployment
- EC2 t3.micro (eu-north-1), Ubuntu 24.04
- Nginx reverse proxy (port 80 → uvicorn 8000 + static frontend)
- systemd service `linkedin-job-hunter`
- Deploy: `git pull && cd frontend && npm run build && sudo systemctl restart linkedin-job-hunter`
- Real IP/account IDs in `infra.local.md` (gitignored); repo keeps `<ec2-ip>` / `<aws-account-id>` placeholders.

## Database (SQLite)
- `jobs` — all scraped jobs with user_id, scoring, applied status
- `cover_letters` — one per job
- `user_profile` — auth + cv_text
- `scheduled_scrapes` — persistent schedules
- `scrape_runs` — run history

## Environment Variables (.env)
- `DATABASE_URL`, `APIFY_API_TOKEN`, `LLM_API_KEY`, `LLM_MODEL`, `SECRET_KEY`
- `SCRAPER_PROVIDER` — `apify` (default) or `brightdata`
- `BRIGHTDATA_API_TOKEN`, `BRIGHTDATA_DATASET_ID`, `BRIGHTDATA_COUNTRY`
- `LLM_REASONING_EFFORT` — extended thinking for scoring only (default off; `high` in prod)

## Common Pitfalls
1. **Assuming global dedup** — `linkedin_id` is unique per `user_id`, not globally. Two users can scrape the same job.
2. **Restarting during a scrape** — kills background tasks mid-flight; the run is lost.
3. **Local Bright Data testing** — fails from WSL due to Cloudflare Gateway TLS interception. Test from EC2.
4. **Forgetting to build frontend** — a backend-only restart doesn't pick up UI changes. Always rebuild `frontend/dist/` when frontend files change.
5. **Bare IP access** — Nginx only serves `vaibing.org`; raw IP returns empty reply by design. Use the domain.
