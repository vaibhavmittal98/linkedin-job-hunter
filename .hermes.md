# LinkedIn Job Hunter

Hermes: when working in this repo, load these project skills. Each lives at `.hermes/skills/<name>/SKILL.md` — use `read_file` to pull the one you need.

## Skills index (load the matching one for your task)

| Task | Skill |
|---|---|
| Architecture, dependencies, conventions, "how does X work" | `project-overview` |
| Cover letters, PDF export, refine chat, style rules | `cover-letters` |
| Scraper, Apify/Bright Data, actor params, field mapping | `scraping` |
| Scoring, criteria weights, disqualifier gate, LLM prompt | `scoring` |
| Scheduling, APScheduler, daily/weekly, missed runs | `scheduling` |
| React UI, components, routing, auth flow, dashboard | `frontend` |
| SQLite schema, WAL mode, migrations, tables | `database` |
| EC2 deployment, Nginx, systemd, backups, SSH | `deployment` |

Reference: `infra.local.md` (gitignored) holds the real EC2 IP and AWS account ID. Repo uses `<ec2-ip>` / `<aws-account-id>` placeholders.

## Key rules
- **Never delete `jobs.db`** without explicit permission. Use ALTER TABLE for schema changes.
- **Don't restart the server mid-scrape** — kills background tasks.
- **Frontend changes need `npm run build`** — backend-only restart won't pick up UI changes.
- **Use `vaibing.org`, never the raw IP** — Nginx only serves the domain.
- **Bright Data testing from local WSL fails** — Cloudflare Gateway blocks it. Test from EC2 or switch to Apify.
- **Jobs are deduped per-user, not globally** — `linkedin_id` + `user_id` composite uniqueness.
- **All app testing/runtime verification must happen on EC2, not locally** — this WSL environment is for code editing only. The backend, database, scraping, and API endpoints are running on the EC2 instance. To test anything: SSH into EC2 and run it there, or hit `vaibing.org` via curl from here. Never try to start the FastAPI server or run scrapes locally.
